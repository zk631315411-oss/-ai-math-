# 10 — KG 资产与认知诊断推理

本文档记录 v4.4 教材知识图谱中已建好但尚未在应用层消费的结构性资产，以及把这些资产接入认知诊断主链路后可形成的差异化能力。它是 [09-竞赛定位与认知诊断闭环.md](./09-竞赛定位与认知诊断闭环.md) 中诊断卡片、断点定位和效果验证的物理基础。

## 一、v4.4 构建管线概览

v4.4 是一套 9 步流水线，从丘维声《高等代数》和同济《高等数学》结构化 Markdown 出发，产出可入库的知识图谱。构建流程见 [教材提取模块/正式脚本/v4.4/v4.4_step说明.md](../教材提取模块/正式脚本/v4.4/v4.4_step说明.md)。

当前图谱规模（据 [README.md](../README.md)）：

- 节点：2,980
- 边：4,396
- 节点类型：9 种（Concept / Theorem / Formula / Method / ProblemClass / RuleCase / ConditionExpression / Outcome / KnowledgeGroup）
- 覆盖教材：高等代数上册、高等代数下册、高等数学上册、高等数学下册

## 二、三大结构性资产

这三项是 v4.4 已经建好、但应用层尚未消费的资产。它们是对手在两个月内难以复刻的结构性优势。

### 资产 1：节点带 `source_code` + `evidence_span`

每个核心节点都带两个溯源字段：

| 字段 | 含义 | 示例 |
|---|---|---|
| `source_code` | 紧凑来源编码，指向教材具体小节 | `gaodai_shang:C03:S05:U01` |
| `evidence_span` | 教材原文片段 | "由 s·m 个数排成 s 行、m 列的一张表称为一个 s×m 矩阵" |

代码位置：[kg_v44.py:54-64](../app/db/kg_v44.py) 的 `_node_map` 把这两个字段从 Neo4j 读出并返回给所有查询函数。`find_node`、`nodes_for_section`、`related_nodes` 均返回它们。

**意义**：诊断结论可以追溯到丘维声教材的具体小节段落，而不是停留在"你薄弱的概念是矩阵的秩"。这让"认知断点诊断"从 LLM 猜测变成有教材出处的可验证判断。

### 资产 2：规则案例层

v4.4 把数学中的条件判断结构化为一组专门的关系，而不是压成一条普通边。结构如下：

```text
定理/公式/方法
  --HAS_RULE_CASE--> 规则案例 RuleCase
  规则案例 --APPLIES_TO--> 适用对象
  规则案例 --HAS_CONDITION--> 条件表达式 ConditionExpression
  规则案例 --HAS_OUTCOME--> 结论/状态 Outcome
  条件表达式 --REFERS_TO--> 核心知识点
```

示例（来自 v4.4_step说明.md:30-35）：

```text
线性方程组解的判定定理 --HAS_RULE_CASE--> 无解判定
无解判定 --APPLIES_TO--> 非齐次线性方程组
无解判定 --HAS_CONDITION--> r(A)<r(A|b)
无解判定 --HAS_OUTCOME--> 线性方程组无解
```

节点类型 `RuleCase`、`ConditionExpression`、`Outcome` 已在 Neo4j 中存在（README:214 确认 9 种节点类型）。

**意义**：当学生做错一道线性方程组解的判定题时，系统可以定位到涉及哪个规则案例，进一步判断学生是对条件理解错了（没验证 r(A)<r(A|b)），还是对结论理解错了，还是对适用对象判断错了。这是结构化推理，不是 RAG 文本检索。对手的 KG 把"若 A 则 B"压成一条边或扔进 RAG 文本，丢了条件结构。

### 资产 3：三层关系架构

v4.4 把关系分为三层（v4.4_step说明.md:294-348）：

| 层 | 关系类型 | 用途 |
|---|---|---|
| 核心普通关系层 | SUPERIOR / EQUATIVE / PART_OF / HAS_PROPERTY / USES / GETS / DERIVES | 学习路径、概念依赖、方法推荐 |
| 条件判断规则层 | HAS_RULE_CASE / APPLIES_TO / HAS_CONDITION / HAS_OUTCOME / REFERS_TO | 条件推理、错因定位 |
| 知识组导航层 | HAS_MEMBER / HAS_ANCHOR | 按小节或规则主题组织节点 |

另有派生/展示层 `PREREQUISITE_OF` 和 `HAS_POSSIBLE_STATE`，v4.4 定义为"可从核心图与规则层推导"，但当前未实现派生逻辑。

**意义**：不同教学用途走不同层。学习路径走核心层，错因诊断走规则层，章节导航走知识组层。对手的 KG 是扁平的，学习路径和例题推荐混在一起。

## 三、当前应用层使用情况

诚实记录：应用层对 v4.4 KG 的消费非常有限。

### 已消费的查询函数（5 个）

全代码库只有 4 个文件调用 `kg_v44`：

| 调用方 | 用的函数 | 用途 |
|---|---|---|
| [diagnostic.py:31](../app/db/diagnostic.py) | `nodes_for_section` | 诊断时取章节概念列表注入 Prompt |
| [diagnostic.py:51](../app/db/diagnostic.py) | `related_nodes` | 取支撑/扩展知识（兼容旧 prerequisite 链） |
| [auth.py:386](../app/routers/auth.py) | `find_node`, `related_nodes` | 知识图谱可视化 API |
| [whitelist_db.py:7](../app/db/whitelist_db.py) | `nodes_for_section`, `nodes_up_to_chapter` | 生成知识边界白名单 |
| [prerequisite_checker.py:13,44](../app/services/prerequisite_checker.py) | `prerequisite_candidates_for_section`, `related_nodes` | 前置缺口检测 |

### 未消费的资产

| 资产 | 现状 |
|---|---|
| `source_code` 字段 | `find_node` / `related_nodes` 返回了它，但路由层和前端不读取，诊断卡片不显示教材出处 |
| `evidence_span` 字段 | 同上，返回了但不消费 |
| 规则案例层（HAS_RULE_CASE 等） | 0 处查询入口。`kg_v44.py` 没有规则案例查询函数 |
| 证明追踪层 | v4.4 设计中未单独实现，当前与核心层混合 |
| 应用索引层 | v4.4 用 `ProblemClass` 节点和 APPLIES_TO 边承载，但应用层不按层过滤 |
| `PREREQUISITE_OF` 派生 | `prerequisite_checker.py:2` 承认 v4.4 不维护严格前置链，用邻接节点代替 |

结论：v4.4 KG 当前被当成一张"概念名表"在用。三大结构性资产都建好了，但没接上电。

## 四、三个杀手级能力 → 代码路径

把上述资产接入应用层后，可形成三个对手没有的能力。

### 能力 1：诊断可溯源

**叙事**：系统说"你卡在矩阵的秩"，同时说"这个概念定义在丘维声《高等代数》上册第 3 章第 5 节第 1 单元，你的前置知识矩阵的初等行变换掌握度只有 stage 1，它在第 3 章第 2 节，建议先回去读 P.87-92"。

**代码路径**：
- `kg_v44.find_node(name)` 已返回 `source_code` 和 `evidence_span`
- 在 `qa.py` 的诊断触发后，把 `source_code` 解析为教材名 + 章节 + 小节
- 在 `prompt_engine.build_prompt` 的诊断干预块中加入教材出处
- 在前端诊断卡片中显示"教材出处"字段

**缺口**：路由层不读取 `source_code`，前端无显示组件。需补一个 `source_code` → 教材页码的解析函数（`textbook_section_db` 已有页码映射表）。

### 能力 2：规则案例推理

**叙事**：学生做错线性方程组解的判定题 → 系统定位到涉及"无解判定"规则案例 → 检查学生是否验证了条件 r(A)<r(A|b) → 输出"你用了无解判定，但前提 r(A)<r(A|b) 没有验证。请先算两个矩阵的秩。"

**代码路径**：
- 新增 `kg_v44.get_rule_cases_for_node(node_name)` 查询函数，返回该节点关联的所有规则案例（含条件、结论、适用对象）
- 在 `error_analyzer.analyze_error` 中，把学生的错误与规则案例的条件比对：学生是否遗漏了某个条件？
- 在 `prompt_engine.build_prompt` 中，把命中的规则案例结构化地注入 Prompt，让 LLM 基于条件-结论图做推理，而不是自由文本猜测

**缺口**：`kg_v44.py` 没有规则案例查询函数。需新增一个 Cypher 查询，走 `HAS_RULE_CASE → APPLIES_TO / HAS_CONDITION / HAS_OUTCOME` 路径。

### 能力 3：教材级闭环

**叙事**：学生卡题 → 定位到 KG 节点（带 source_code）→ 查规则案例判断断点类型 → source_code 指向教材具体小节 → 从该小节的 ProblemClass 节点推荐教材原题 → 学生做题 → stage 更新 → 重新检查前置链是否打通。

**代码路径**：
- 诊断 → `find_node` 返回 `source_code` → 解析为 `sequence_id`
- 推荐练习 → `nodes_for_section` 取该小节的 `ProblemClass` 节点 → `exercise_bank_db` 按知识点取教材原题
- 学生做题 → `exercise.py` 批改 → `update_stage` → `prerequisite_checker` 重新检查前置

**缺口**：当前 `exercise.py` 的出题是 LLM 生成，不是从 KG 的 `ProblemClass` 节点取教材原题。`exercise_bank_db` 有按 `sequence_id` 取题的 `list_by_sequence_id` 函数（exercise.py:166 已调用），但只取已有题库，不查 KG。

## 六、与 09 文档的关系

09 文档定义了认知诊断闭环的叙事主线和诊断卡片形态，但诊断卡片的数据来源描述仍停留在 v4.2 时代的扁平图理解（"Neo4j：提供知识点、前置关系和后续路径"）。本文档补充了诊断卡片的物理基础：

- "判断依据"字段 ← `evidence_span`（教材原文片段）
- "教材出处"字段 ← `source_code`（教材小节坐标）
- "错因类型"字段 ← 规则案例层的条件检查
- "后续练习"字段 ← KG 应用索引层的 `ProblemClass` 节点

09 中的"效果验证"部分（诊断一致率、提示后修正率）也应基于本文档的溯源能力：系统诊断是否与教师诊断一致，关键看系统能否定位到与教师相同的规则案例和条件断点。
