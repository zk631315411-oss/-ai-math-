# 智学助手教材知识图谱建构规则 v4.2

> 版本日期：2026-06-18  
> 核心思路：以数学知识图谱文献的节点和关系类型作为本体约束，以 Tree-KG 的教材树构建思想作为流程框架；默认在本地复现 Tree-KG 流程，清华 Tree-KG API 作为可选 adapter，最终结果根据智学助手的应用目标进行归一化、审核和入库。

---

## 一、v4.2 总体判断

v4.2 不再继续沿用 v4.1 的“LLM-first，validator-gated”作为主表达。v4.2 的核心口径调整为：

> **数学本体约束 + 教材树驱动 + 本地 Tree-KG 式构建 + 显式/隐式分层 + 人工审核入库。**

其中：

- 数学本体约束：参考《基于多源异构数据融合的初中数学知识图谱构建》中提出的数学实体和关系类型。
- 教材树驱动：参考 Tree-KG，将教材目录结构作为知识图谱骨架。
- Tree-KG 构建：默认在本地复现 Tree-KG 的教材结构解析、摘要生成、实体关系抽取和扩展流程；清华 Tree-KG API 若获得授权，可作为可选输入源。
- 显式/隐式分层：区分教材原文直接支持的显式 KG 与模型推断得到的隐式扩展 KG。
- 人工审核入库：最终进入 Neo4j 主图的节点和边必须经过 schema 归一化、硬规则校验和必要的人工审核。

一句话概括：

```text
论文给本体，Tree-KG 给流程，DeepSeek 负责本地抽取，智学助手决定取舍和入库标准。
```

## 二、KG 在智学助手中的定位

智学助手中的教材知识图谱不是数学百科，也不是教材全文结构化副本，而是面向教学应用的知识导航层。

主要服务三个场景：

1. 学生不会某题时，追溯可能缺失的知识点。
2. 按教材章节和知识依赖生成学习路径。
3. 围绕某个知识点推荐相关例题、方法和题型。

因此，v4.2 建图的目标不是“抽出教材中所有可命名短语”，而是形成可用于诊断、导航和推荐的教学知识结构。

## 四、v4.2 节点类型

### 4.1 正式节点类型

v4.2 正式节点类型如下：

| 类型 | 中文名 | 来源 | 说明 |
|---|---|---|---|
| Concept | 概念 | 沿用数学 KG 文献 | 数学对象、性质、结构、状态被专题化后形成的知识点 |
| Method | 方法 | 沿用数学 KG 文献 | 解题方法、证明方法、计算方法、判别方法 |
| Formula | 公式 | 沿用数学 KG 文献 | 可被调用的公式、恒等式、计算式 |
| Theorem | 定理 | 沿用数学 KG 文献 | 定理、命题、引理、推论、准则等结论性知识 |
| ProblemClass | 题型/问题类 | 智学助手扩展 | 应用节点，用于例题推荐、错题追溯和练习导航 |

### 4.2 为什么补充 ProblemClass

数学 KG 文献中没有单独设置题型节点，但智学助手需要支持：

- 不会某题时追溯知识点。
- 某知识点推荐相关题型。
- 题型推荐对应方法和例题。

因此需要补充 ProblemClass，例如：

```text
线性方程组求解问题
行列式计算问题
矩阵秩计算问题
证明向量组线性无关问题
```

ProblemClass 是应用节点，不与 Concept、Theorem、Formula、Method 完全同层。它不应泛化为所有习题题干，而应表示可复用的问题类型。

### 4.3 Definition 不作为独立节点

Definition 不作为正式节点类型。

原因：

1. 定义通常是知识点的说明文本，而不是独立知识对象。
2. 若将“某概念的定义”作为节点，会产生大量形式化节点，增加图谱噪音。
3. 智学助手真正需要检索和诊断的是“线性相关”“可逆矩阵”“矩阵的秩”等知识点，而不是“线性相关的定义”这一文本形式。

处理方式：

```text
定义句 -> 挂载到对应节点的 definition / description / evidence 字段。
```

示例：

```json
{
  "name": "线性相关",
  "type": "Concept",
  "definition": "教材中的原文定义",
  "evidence": "定义所在原文片段"
}
```

### 4.4 属性/状态类内容的处理

“唯一解”“无解”“零解”“可逆”“线性相关”“线性无关”等内容默认不因出现一次就成为独立节点。

默认处理：

```text
属性/状态 -> 作为相关节点的属性、状态标签或 evidence。
```

升级为 Concept 的条件：

满足以下任一条件时，可以升级为正式 Concept 节点：

1. 教材对该状态或性质给出明确界定。
2. 存在独立判别准则。
3. 后文以它为主题展开讨论。
4. 它在多条关系中承担连接作用。
5. 它是学生可能单独卡住、复习或练习的对象。

示例：

```text
“无解”若只是线性方程组解的状态，作为属性处理。
“无解当且仅当增广矩阵的秩大于系数矩阵的秩”若作为判别准则被教材展开，则“线性方程组无解”可升级为 Concept。
```

### 4.5 典型例题不直接按普通节点抽取

典型例题不再与内容精华共用同一套节点抽取逻辑。原因是例题中的知识形态与正文不同：正文主要给出概念、定义、定理、公式和一般方法；例题主要展示“某类问题如何被解决”，其中既有题型，也有方法、工具使用和中间计算过程。

因此 v4.2 后续流程中，典型例题先抽取 `ExampleFrame`，再由 `ExampleFrame` 转换出应用层节点和边。

`ExampleFrame` 不是正式图谱节点类型，而是中间结构，主要包含：

| 字段 | 含义 | 示例 |
|---|---|---|
| example_label | 例题编号或位置 | 例3 |
| problem_class | 题型/问题类 | 行列式计算问题 |
| methods | 解题方法 | 加边法、递推法、数学归纳法 |
| tool_uses | 使用的公式、定理、方法或概念 | 使用范德蒙行列式公式 |
| gets | 解题过程中得到的对象、形式或结论 | 得到递推关系、化为上三角行列式 |
| evidence | 对应原文证据 | 连续原文片段 |

处理原则：

```text
例题标题、解法标题、方法名提示，可以证明“存在某方法”。
但不能单独证明“该方法使用了某公式/定理”。
```

例如：

```text
解法二（加边法）。
```

可以支持：

```text
加边法 -> Method 候选
加边法计算行列式问题 --USES--> 加边法
```

但不能单独支持：

```text
加边法 --USES--> 行列式按列展开公式
```

后者必须从后续连续解题过程里寻找证据，例如“按某行/列展开”“为了利用范德蒙行列式的计算公式”等明确表述。

## 五、v4.2 边类型

### 5.1 结构边

结构边来自 Tree-KG 的教材树思想。

| 边类型 | 含义 | 说明 |
|---|---|---|
| HAS_SUBSECTION | 章节包含子章节 | 章、节、小节之间的树状结构 |
| INTRODUCES | 小节引入知识节点 | 对应 Tree-KG 中 has_entity 的教学化表达 |
| HAS_EXAMPLE | 小节包含例题 | 用于例题索引，不直接表示知识依赖 |

### 5.2 核心知识边

核心知识边以数学 KG 文献的四类关系为基础，并补充高等数学教材中常见的推导来源关系。

| 边类型 | 来源 | 含义 |
|---|---|---|
| SUPERIOR | 沿用文献 superior | 上位/下位关系 |
| EQUATIVE | 沿用文献 equative | 同位/同层/同类关系，默认进入推荐层/弱关系层 |
| USES | 沿用文献 use | 一个知识对象、题型或问题解决过程需要借助某公式、定理或方法 |
| GETS | 沿用文献 get | 通过某公式、定理或方法得到某概念、结论或对象 |
| DERIVED_FROM | 智学助手扩展 | 定理、公式、结论之间存在推导来源 |

Step 5 入主图前还需要加硬闸门：

```text
SUPERIOR 只表示同类知识点之间的上位/下位关系。
“某性质/定理属于某章节主题”不能自动视为 SUPERIOR。
例如：
两行相同行列式值为0 --SUPERIOR--> n阶行列式
这类边应退回 review，通常不入主图，或改作章节 INTRODUCES / evidence。
```

```text
USES 必须表示 source 真正借助 target。
若原文只是“这首先需要 A 和 B 的概念”，A 与 B 是并列需求，不能自动抽成 A --USES--> B。
例如：
k阶子式 --USES--> 余子式
证据只是“需要 k 阶子式和它的余子式的概念”时，应退回 review。
```

### 5.3 USES 与 APPLIES_TO

v4.2 不将 APPLIES_TO 作为底层边类型。

理由：

```text
A --USES--> B
```

表示 A 需要使用 B。

若要表达“B 可应用于 A”，可以通过反向查询 USES 得到。

示例：

```text
线性方程组求解问题 --USES--> 初等行变换法
行列式计算问题 --USES--> 行列式按行展开
```

查询“初等行变换法应用于哪些题型”时：

```cypher
MATCH (p)-[:USES]->(m {name: "初等行变换法"})
RETURN p
```

因此，APPLIES_TO 只作为展示层表达，不作为底层 schema。

### 5.4 EQUATIVE 不是数学等价

文献中的 equative 指“同位关系”，不是数学上的等价关系。

例如：

```text
三角形 与 四边形
正弦定理 与 正切定理
完全平方公式 与 平方差公式
```

这些是同层、同类、并列关系，不是逻辑等价。

因此 v4.2 中：

```text
EQUATIVE = 同位/同层/同类关系
```

EQUATIVE 主要服务推荐和横向扩展，不作为学习路径主干关系。默认入弱关系层或推荐层，除非人工确认其对当前教学导航有明确价值。

如果后续确实需要表达“同义、等价、可互换表述”，应作为归一化阶段的 alias / same_as 处理，不混入 EQUATIVE。

### 5.5 GETS 与 DERIVED_FROM 的边界

GETS 和 DERIVED_FROM 都表达“由某些知识得到另一些知识”，但使用场景不同，必须严格区分。

```text
GETS：
偏应用、解题、计算、化简、构造。
表示通过某公式、定理或方法，得到某个对象、数值、形式、概念或结果。

DERIVED_FROM：
偏理论证明、定理推导、公式推导。
表示某个定理、公式、命题或理论结论，在证明结构上来源于另一个定理、公式或结论。
```

GETS 示例：

```text
线性方程组求解问题 --USES--> 初等行变换法
初等行变换法 --GETS--> 行阶梯形矩阵

代入法 --GETS--> 一元二次方程
求根公式 --GETS--> 实数根
勾股定理 --GETS--> 直角三角形的边长
```

这些关系强调“解题过程中得到什么”。

DERIVED_FROM 示例：

```text
克莱姆法则 --DERIVED_FROM--> 行列式性质
矩阵秩不因初等行变换改变 --DERIVED_FROM--> 初等矩阵可逆性
齐次线性方程组解空间维数定理 --DERIVED_FROM--> 线性映射核与像的维数关系
```

这些关系强调“理论上由什么推出”。

判别规则：

```text
如果教材语境是“用某方法/公式求出、化为、得到某对象”，优先判为 GETS。
如果教材语境是“由定理 A 可得定理 B、根据命题 A 推出结论 B、证明中引用 A”，优先判为 DERIVED_FROM。
```

### 5.6 PREREQUISITE_OF 的位置

v4.2 不把 PREREQUISITE_OF 作为 LLM 优先直接抽取的原始关系。

原因：

1. v4.1 中 LLM 容易把“先出现”误判为“前置”。
2. 前置关系本质上是教学导航关系，可以由其他知识关系推导或经人工审核生成。
3. superior、use、get、derived_from 等关系都可能支持前置推断。

处理方式：

```text
PREREQUISITE_OF = 派生导航边
```

生成来源：

- SUPERIOR 反向推断：上位知识通常是下位知识的前置。
- USES 推断：被使用的公式、定理、方法通常是使用对象的应用前置。
- GETS 推断：得到某概念所需的公式、定理、方法可作为前置。
- DERIVED_FROM 推断：推导来源通常是被推导结论的证明前置。
- 教师/人工审核补充。

示例：

```text
正方形 --SUPERIOR--> 四边形
可派生：四边形 --PREREQUISITE_OF--> 正方形

线性方程组求解问题 --USES--> 初等行变换法
可派生：初等行变换法 --PREREQUISITE_OF--> 线性方程组求解问题
```

派生出的 PREREQUISITE_OF 需要标注来源：

```json
{
  "type": "PREREQUISITE_OF",
  "derived_from": "USES",
  "confidence": 0.82,
  "requires_review": true
}
```

## 六、LLM 与 Tree-KG API 在 v4.2 中的角色

### 6.1 DeepSeek 模型使用策略

v4.2 默认使用 DeepSeek API，在工程实现中优先使用低成本模型。

默认策略：

```json
{
  "default_model": "deepseek-flash",
  "high_risk_model": "deepseek-flash",
  "allow_pro": false
}
```

也就是说，第一阶段先全流程使用 flash 跑通，不默认启用 Pro。

flash 适用环节：

```text
1. 小节摘要生成
2. 显式节点抽取
3. 显式关系抽取
4. Definition 挂载
5. 属性/状态初判
6. 隐式候选边初判
7. review 辅助建议
```

可选升级到 Pro 的高风险环节：

```text
1. GETS 与 DERIVED_FROM 的边界判断
2. DERIVED_FROM 方向判定
3. 属性/状态是否升级为 Concept 的争议样本
4. 高风险同义合并
5. 人工 review 前的二次复核
```

但是否启用 Pro 由配置控制。只有当 flash 在抽样审核中表现明显不稳定时，才切换对应环节。

### 6.2 清华 Tree-KG API 的定位

清华 Tree-KG API 作为可选 adapter，不作为 v4.2 默认依赖。

如果后续获得有效调用权限，Tree-KG API 可负责：

1. 教材结构解析。
2. 章节/小节摘要生成。
3. 实体抽取。
4. 关系抽取。
5. 实体去重。
6. 实体聚合。
7. 边预测。
8. 输出可扩展 KG 结果。

但即使 Tree-KG API 可用，智学助手 v4.2 仍负责：

1. 提供教材和配置。
2. 读取 Tree-KG 输出结果。
3. 将 Tree-KG 输出映射到数学本体。
4. 校验节点类型和边类型。
5. 区分显式边与隐式扩展边。
6. 生成 review 队列。
7. 导入 Neo4j 主图或弱关系层。

如果 Tree-KG API 不可用，则本地脚本使用 DeepSeek 复现 Tree-KG 核心流程：

```text
教材树解析 -> 小节摘要 -> 实体抽取 -> 关系抽取 -> 规范化 -> 去重 -> 边预测
```

工程落地时必须拆分职责：小节摘要阶段只整理摘要、术语和原文证据片段，不直接输出正式节点候选或关系候选；显式节点抽取和显式关系抽取分别由后续独立脚本完成。

### 6.3 Tree-KG API 调用输入

调用 Tree-KG 服务时，需要准备：

```text
1. 教材文件
2. user_config.json
3. 教材页码范围
4. 目录页码范围
5. 正文页码范围
6. 目录最大层级
7. 目录匹配正则
```

示例配置结构：

```json
{
  "course_name": "Advanced Algebra",
  "material_name": "高等代数上册.pdf",
  "book_start_page": 1,
  "book_end_page": 500,
  "cover_start_page": 1,
  "cover_end_page": 1,
  "toc_start_page": 2,
  "toc_end_page": 8,
  "text_start_page": 9,
  "text_end_page": 480,
  "appendix_start_page": 481,
  "appendix_end_page": 500,
  "toc_max_level": 3,
  "toc_re_expression": [
    "(第\\d+章.*\\n\\n)",
    "(\\d+\\.\\d+.*\\n\\n)",
    "(\\d+\\.\\d+\\.\\d+.*\\n\\n|.+?\\n\\n)"
  ]
}
```

实际配置需要按具体教材页码和目录格式调整。

### 6.4 Tree-KG 输出的归一化要求

Tree-KG 可能输出自由关系标签，例如：

```text
contains
has
depends_on
uses
derives
related_to
applies
```

这些标签不能直接进入智学助手主图，必须映射到 v4.2 schema。

示例映射：

| Tree-KG 输出 | v4.2 归一化 |
|---|---|
| has_subsection / contains section | HAS_SUBSECTION |
| has_entity / introduced_in | INTRODUCES |
| is_a / belongs_to / subtype | SUPERIOR |
| same_level / sibling / parallel | EQUATIVE |
| use / applies / depends_on_tool | USES |
| get / obtains / derives_result | GETS |
| derived_from / proof_uses / follows_from | DERIVED_FROM |
| related_to / associated_with | 不自动入主图，进入 review |

原则：

```text
无法稳定映射的自由关系，不进入主图。
```

### 7.2 显式 KG 与隐式 KG

v4.2 必须区分显式 KG 和隐式 KG。

显式 KG：

```text
教材原文直接支持的节点和边。
```

可以进入主图。

隐式 KG：

```text
Tree-KG 通过语义相似度、共同章节祖先、共同邻居、边预测等方式推断出的潜在关系。
```

默认进入候选层或弱关系层，不直接进入主图。

处理规则：

| 类型 | 入库策略 |
---|---|
| 显式节点 | 可进入主图 |
| 显式边 | 可进入主图 |
| 隐式节点 | 原则上 review 后入图 |
| 隐式边 | 默认进入 weak_edges 或 review |
| 无 evidence 的自由关系 | 不进入主图 |

### 7.2.1 阶段一分层产物

当前第 2 章样本先采用“显式图优先”的阶段一策略。阶段一不做隐式边预测，不生成 PREREQUISITE_OF 派生边，只把已抽取结果整理成清晰的分层候选包。

阶段一分层如下：

| 层 | 含义 | 入库策略 |
|---|---|---|
| explicit_core | 教材正文直接支持的核心节点和边 | 可进入核心主图候选 |
| example_application | 由典型例题转换出的题型、方法和使用关系 | 用于推荐层候选，不进入学习路径主干 |
| review_pending | 需要人工或辅助模型审批的节点和边 | 不入库，等待 Step 7 统一决策 |
| rejected_archive | 已被硬规则拒绝、重复或被替代的候选 | 不入库，但保留审计记录 |
| implicit_deferred | 隐式扩展边、弱关系、前置派生 | 阶段一暂不生成，只预留 schema |

处理原则：

```text
1. explicit_core 只收纳 kg_layer=core 且 step5_status=main 的节点和边。
2. example_application 在阶段一只收纳 kg_layer=example_application 且已通过 review 决策的节点和边；未审批前进入 review_pending。
3. review_pending 汇总 Step 3、Step 4 和 Step 5 传递下来的待审项。
4. rejected_archive 保留所有拒绝项和重复项，不能无声删除。
5. implicit_deferred 本轮不生成，避免在显式主图尚未稳定前放大 review 负担。
6. Step 3D 只做同义规范化、稳定 id 生成和可追溯的核心节点对齐，不做提前审批；不得在 Step 3D 静默删除、改写或决定候选是否入库。
7. 应用层归一化产生的自环、临时工具节点边、可疑方法边，应进入 Step 5/Step 7 的 review 或 rejected_archive，不得无审计地消失。
```

因此，阶段一的 Step 6 输出不是最终入库包，而是 Step 7 审核决策的输入。

### 7.3 前置关系生成流程

PREREQUISITE_OF 不作为 Tree-KG 原始抽取目标。

生成流程：

```text
SUPERIOR / USES / GETS / DERIVED_FROM
        │
        ▼
前置候选生成
        │
        ▼
规则过滤
        │
        ▼
人工审核 / LLM 辅助审核
        │
        ▼
PREREQUISITE_OF 导航边
```

前置边必须带来源：

```json
{
  "source": "初等行变换法",
  "target": "线性方程组求解问题",
  "type": "PREREQUISITE_OF",
  "derived_from_edge": "线性方程组求解问题 --USES--> 初等行变换法",
  "layer": "navigation",
  "requires_review": true
}
```

### 7.4 典型例题 ExampleFrame 流程

典型例题的工程流程调整为：

```text
典型例题原文
        │
        ▼
ExampleFrame 抽取
        │
        ├─ 例题编号/题干
        ├─ 题型 ProblemClass
        ├─ 方法 Method
        ├─ 工具使用 tool_uses
        └─ 得到结果 gets
        │
        ▼
应用层节点/边候选
        │
        ├─ ProblemClass 节点
        ├─ Method 节点
        ├─ ProblemClass --USES--> Method
        ├─ ProblemClass/Method --USES--> Formula/Theorem/Method
        └─ Method --GETS--> Concept/Formula/Theorem/ProblemClass
        │
        ▼
review 队列
        │
        ▼
归一化后入库
```

关键约束：

1. 典型例题中抽出的 `ProblemClass` 和 `Method` 默认进入 review。
2. `ProblemClass --USES--> Method` 可以由“解法二（加边法）”这类方法标题支持。
3. `Method --USES--> Formula/Theorem` 必须由后续解题过程中的连续原文支持，不能只由方法标题支持。
4. 例题中的一次性答案、单次数值、中间计算式默认不转成正式节点。
5. 例题中的工具使用若无法匹配到正文核心节点，只保留在 `ExampleFrame` 中，等待后续归一化或人工处理。
6. 若归一化后出现 `Method --USES--> Method` 自环，例如“按行列展开法 --USES--> 按行列展开法”，应进入 Step 7 判断是否改写为 `Method --USES--> Formula/Theorem`，不能在 Step 5 直接硬删。

示例：

```text
原文：解法二（加边法）。
处理：
1. 抽取 Method：加边法
2. 抽取 ProblemClass：加边法计算行列式问题
3. 生成边：加边法计算行列式问题 --USES--> 加边法
4. 若后文出现“为了利用范德蒙行列式的计算公式……”，再生成：
   加边法转化为范德蒙行列式问题 --USES--> 范德蒙行列式公式
```

## 九、质量闸门

### 9.1 自动准入条件

节点自动进入主图需要同时满足：

1. 类型属于 v4.2 节点枚举。
2. 名称不是“定理1”“公式2”“命题3”等纯编号名。
3. evidence 能回到教材原文或 Tree-KG 输出中可追溯的章节文本。
4. 不是例题中的一次性结论。
5. 不是默认应作为属性/状态的短语。
6. 置信度达到阈值。

边自动进入主图需要同时满足：

1. 类型属于 v4.2 边枚举。
2. source 和 target 都是已准入节点。
3. 方向符合关系定义。
4. evidence 或 Tree-KG 关系说明可追溯。
5. 不是无法归一化的自由标签。
6. 隐式边不自动进入主图，除非达到高置信度且通过审核。

### 9.2 必须 review 的情况

以下情况必须进入 review：

1. Tree-KG 输出的自由关系无法稳定映射。
2. 节点类型在 Concept / Method / ProblemClass 之间摇摆。
3. 属性/状态是否升级为节点不明确。
4. 同义合并可能造成粒度合并错误。
5. DERIVED_FROM 方向不明确。
6. 隐式边候选。
7. 派生 PREREQUISITE_OF 边。
8. 例题中抽出的 Method 或 ProblemClass。

## 十、v4.2 与 v4.1 的核心区别

| 维度 | v4.1 | v4.2 |
|---|---|---|
| 主口径 | LLM-first，validator-gated | 数学本体约束 + Tree-KG 构建 |
| 教材结构 | 作为 metadata 和章节来源 | 作为图谱骨架 |
| 节点类型 | 概念、定义、定理、公式、方法、题型、属性值 | 概念、方法、公式、定理、题型 |
| Definition | 可能作为节点 | 只作为字段/evidence |
| 属性/状态 | 默认属性，满足条件升级 | 保留该规则，但并入 Concept 升级逻辑 |
| APPLIES_TO | 独立关系 | 不作为底层边，使用 USES 反向查询 |
| PREREQUISITE_OF | 可由 LLM 抽取并审核 | 主要作为派生导航边 |
| 关系标签 | 自定义关系较多 | 以 superior/equative/use/get 为核心 |
| Tree-KG | 未纳入主流程 | 默认本地复现 Tree-KG 式流程，API 仅作为可选 adapter |
| 隐式边 | 未明确分层 | 显式/隐式分层处理 |
| 例题处理 | 与正文共用抽取逻辑 | 先抽 ExampleFrame，再转换为题型、方法和应用关系 |

## 十一、当前阶段的执行建议

v4.2 不应立即全量替换 v4.1 代码。建议先做一章试验：

1. 准备一章教材 PDF 或 structured 文本。
2. 编写 v4.2 本地配置文件。
3. 运行本地 Tree-KG 式流程：教材树、摘要、节点、关系、归一化。
4. 保存中间输出到：

```text
D:\ai-math\教材提取模块\正式脚本\v4.2\中间产物
```

5. 编写归一化脚本，将本地 LLM 输出或 Tree-KG API 输出映射到 v4.2 schema。
6. 对比 v4.1 同章结果：

```text
节点数量
关系数量
节点类型分布
关系类型分布
错误样例
review 数量
学习路径可用性
```

7. 决定是否扩大到全书。

若后续获得清华 Tree-KG API 权限，可将第 3 步替换为 API adapter 调用，但其输出仍必须经过第 5 步归一化。

## 十二、最终原则

v4.2 的最终原则如下：

```text
1. 不让 LLM 自由发明教学 schema。
2. 不直接照搬 Tree-KG 的自由关系标签。
3. 不把定义句形式化成节点。
4. 不把前置关系当作普通文本关系直接抽取。
5. 不把隐式边无审核地放入主图。
6. 先用数学 KG 本体约束，再用 Tree-KG 构建和扩展。
7. 最终图谱必须服务学习路径、知识追溯和例题推荐。
```
