# 条件判断相关文献速读

本目录用于回答一个具体问题：数学教材知识图谱中，“若条件 P，则结论 Q”这类知识应如何图谱化。

## 已下载材料

1. `2021_Biomedical_Knowledge_Graphs_Construction_From_Conditional_Statements.pdf`
   - 主题：从生物医学条件语句构建知识图谱。
   - 关键做法：不把条件丢进普通边的 evidence，而是显式区分 fact tuple 与 condition tuple。
   - 图谱结构：三层结构。
     - 底层：concept / attribute 节点。
     - 中层：fact tuple / condition tuple 节点。
     - 顶层：statement 节点，连接一组事实元组和条件元组。
   - 启发：条件是事实成立的上下文，不能只作为边描述文本隐藏起来。

2. `2024_Generative_Models_for_Automatic_Medical_Decision_Rule_Extraction_from_Text.pdf`
   - 主题：从医疗指南/教材文本中自动抽取医学决策规则。
   - 关键做法：把医学决策规则建模为二叉决策树。
   - 节点类型：condition node 与 decision node。
   - 每个节点可以包含一个或多个关系三元组，并用 AND / OR 组合。
   - 启发：如果文本本身是分支判定或分情况讨论，可以用“条件节点 -> 决策/结论节点”的树结构表达。

3. `2026_Ontology_based_KG_for_Industrial_Standards_with_Hierarchical_and_Conditional_Structuring.pdf`
   - 主题：工业标准文档中条件语句、表格规则和数值约束的 KG 构建。
   - 关键做法：创建 case 节点；把条件和结论都连接到 case 节点，而不是直接把条件连到结论。
   - 关系类型：
     - `has_condition`
     - `has_condition_AND`
     - `has_condition_OR`
     - `has_consequence`
     - `has_consequence_AND`
     - `has_consequence_OR`
   - 对混合逻辑：引入 `logic_group` 节点保存 AND / OR 的嵌套结构。
   - 典型形式：
     ```text
     case1 --has_condition_AND--> C1
     case1 --has_condition_AND--> logic_group1
     logic_group1 --has_condition_OR--> C2
     logic_group1 --has_condition_OR--> C3
     case1 --has_consequence--> C4
     ```
   - 启发：这篇最接近我们的数学教材条件判断问题。它明确说不要直接连接 conditions 与 consequences，而是通过 case 节点保存条件-结论结构。

4. `2024_Human_Evaluation_of_Procedural_KG_Extraction_from_Text_with_LLMs.pdf`
   - 主题：用 LLM 从过程性文本中抽取步骤、动作、对象、设备、时间，并按预定义 ontology 生成 KG。
   - 关键做法：prompt chaining，两步走。
     - 第一步：生成半结构化过程知识。
     - 第二步：按 ontology 转成 RDF KG。
   - 启发：复杂知识不要一次性直接生成最终图；先生成中间结构，再转图。这支持我们 v4.2 的“先结构化，再入图”方案。

5. `2006_W3C_Defining_N_ary_Relations_on_the_Semantic_Web.html`
   - 主题：语义网中如何表示非二元关系。
   - 关键启发：当关系不只是 source-target 两端，而需要额外成分时，应把关系实体化/重述为一个中间节点。
   - 对我们：条件判断至少包含适用对象、条件、结论、依据、证据，是典型 n 元关系，不适合只用普通二元边表达。

6. `2004_W3C_SWRL_Semantic_Web_Rule_Language.html`
   - 主题：SWRL 规则语言。
   - 关键形式：antecedent/body -> consequent/head。
   - 对我们：数学里的“若 P，则 Q”可以理解为 body/head 结构。

7. `2013_W3C_RIF_Overview.html`
   - 主题：规则交换格式。
   - 关键启发：规则层可以与事实图层分开，规则可用于交换和推理。

8. `2017_W3C_SHACL_Advanced_Features_Rules.html`
   - 主题：SHACL 规则和约束。
   - 关键启发：条件判断可以作为约束/规则层存在，不必全部压进普通知识边。

## 对我们当前问题的结论

相关文献不是没有，而且结论比较一致：

```text
条件判断不应只作为普通二元边的 evidence 保存。
```

原因是条件判断通常不是简单的 A -> B，而是：

```text
case / rule / statement
  - applies_to: 适用对象
  - condition: 条件
  - consequence / outcome: 结论
  - logic: AND / OR / 分支
  - evidence: 原文证据
```

## 三种可选建模方式

### 方案 A：condition tuple / fact tuple 三层结构

对应生物医学条件语句论文。

适合科学陈述：

```text
statement1
  -> fact tuple: A increases B
  -> condition tuple: under C
```

优点：信息无损，适合复杂科学语句。
缺点：对数学教材略重。

### 方案 B：decision tree 决策树结构

对应医疗决策规则论文。

适合多层 if/else 分支：

```text
Condition1
  yes -> Condition2
  no -> DecisionA
```

优点：适合临床指南、算法流程、分步判定。
缺点：数学教材中很多定理不是完整决策树，直接套用会偏重。

### 方案 C：case 节点 + condition/consequence 边

对应工业标准 KG 论文。

适合我们的数学教材：

```text
case1 --has_condition--> r(A)<r(A|b)
case1 --has_consequence--> 线性方程组无解
case1 --applies_to--> 非齐次线性方程组
case1 --supported_by--> 线性方程组解的判定定理
```

优点：
- 比普通状态边严谨。
- 比完整规则语言轻量。
- 能保留 Neo4j 里的直观查询。
- 容易从 LLM 输出 JSON 转换。

## 对 v4.2 的建议

推荐采用“轻量 case/rule_case 结构”。

在抽取阶段先保存为节点字段：

```json
{
  "name": "线性方程组解的判定定理",
  "type": "Theorem",
  "rule_cases": [
    {
      "case_name": "无解判定",
      "applies_to": "非齐次线性方程组",
      "conditions": ["r(A)<r(A|b)"],
      "logic": "AND",
      "outcomes": ["线性方程组无解"],
      "evidence_span": "原文连续片段"
    }
  ]
}
```

入 Neo4j 时可以有两种层次：

1. 初期轻量版：`rule_cases_json` 作为 Theorem 节点属性。
2. 应用需要时展开：

```text
(:Theorem)-[:HAS_RULE_CASE]->(:RuleCase)
(:RuleCase)-[:APPLIES_TO]->(:Concept)
(:RuleCase)-[:HAS_CONDITION]->(:ConditionExpression)
(:RuleCase)-[:HAS_OUTCOME]->(:Outcome)
```

同时可派生展示边：

```text
非齐次线性方程组 --HAS_POSSIBLE_STATE--> 线性方程组无解
```

但这条边应标记为 derived/display，不作为核心推理依据。

## 给薛老师请教时可以这样说

我查到一些条件关系和规则抽取文献，比较常见的做法不是把“条件判断”压成普通二元边，而是引入 statement/case/rule 节点，把条件和结论分别连接到这个中间节点。比如工业标准 KG 会创建 case 节点，再用 has_condition 和 has_consequence 表示条件与结果。我的问题是：数学教材知识图谱中，像“r(A)<r(A|b) 则线性方程组无解”这类内容，是否也适合采用类似 case/rule_case 结构？还是您更建议保留为“知识点—状态”边，并把条件放在边属性中？
